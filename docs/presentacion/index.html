CI/CD · GitHub Actions como columna vertebral

Cuando un equipo abre un Pull Request, este es el flujo que debería ejecutarse:

1

Pull Request

Un repo abre un PR contra develop

2

Llama plantillas

Workflows reusables de Skorify_DevOps

3

Ejecuta controles

Lint · tests · SCA · build

4

Calidad uniforme

Mismo estándar en Frontend, Backend y Data

Mensaje a los tres equipos: alineen sus pipelines a las plantillas de Skorify_DevOps. Llamen los reusable con workflow_call y los composite con uses: ./actions/.... No reinventen workflows.

DevOps se compromete a que para el viernes esté funcional. Si no, llamen a Steevens. (Es chiste. Para el viernes lo tenemos.)

(1 min 30 s) Lean el diagrama paso a paso: cualquier repo abre un PR (1), el repo llama las plantillas oficiales que viven en Skorify_DevOps (2), esas plantillas ejecutan lint, tests, escaneo de vulnerabilidades y build (3), y al final los tres repos quedan bajo el mismo control de calidad (4). Lo barato no es GitHub Actions, es la disciplina: 11 reusable workflows con convención `shared--stage-componente.yml` y 6 composite actions con un solo dueño. El mensaje para frontend, backend y data es directo: no reinventen un linter en cada repo, no escriban su propio escaneo. Llamen al reusable con `workflow_call` y al composite con `uses: ./actions/...`. El frontend ya empezó. Y el chiste con cariño: DevOps se compromete a que el viernes esté funcional, si no llamen a Steevens. Pausa para reírse — y sí, para el viernes lo tenemos.

CI ya tiene código

Workflow SCA con Trivy · rama develop · reusable. 

name: "Shared: SCA - Escaneo de vulnerabilidades"

on:
  workflow_call:

jobs:
  sca-scan:
    runs-on: ubuntu-latest
    container:
      image: aquasec/trivy:0.70.0
      options: --entrypoint /bin/sh
    steps:
      - name: Checkout del código
        uses: actions/checkout@v4

      - name: Ejecutar Trivy para escaneo de vulnerabilidades
        run: trivy fs --scanners vuln,secret,misconfig .

.github/workflows/shared--sca-generic.yml · escanea vulnerabilidades, secrets y misconfigurations.

(1 min) Esto es real, está en `develop`. Un solo workflow reusable, container fijado a Trivy 0.70.0 (versión inmutable), tres scanners en una pasada — vulnerabilidades, secretos, misconfigurations. Cualquier repo de aplicación lo invoca con `workflow_call`. Lo importante no es Trivy en sí — es que la plantilla es reusable y los tres equipos la consumen igual.

CD · cuando el merge se vuelve deploy

Lo que viene en Fase 1 · ADR-CICD-0003 · ADR-INFRA-0005 · ADR-CICD-0008.

1

Merge a la rama

develop · release/* · main
solo main con protección y required reviewers

2

Build empaquetado

Next.js bundle · Lambda zip · librería versionada

3

OIDC a AWS

Sin secretos largos · token efímero por workflow

4

Deploy con CDK / SAM

Al ambiente que la rama indica

Hoy esto no está construido. Es la Fase 1 que arranca cuando se firme OIDC (ADR-INFRA-0005). Sin esa firma, cada deploy seguiría dependiendo de credenciales largas en secretos de GitHub.

(1 min 30 s) Esto es la otra mitad. CI valida — CD despliega. Cuando un merge entra a una rama de integración (develop, release o main), el pipeline empaqueta el artefacto: bundle de Next.js para el frontend, zip de Lambda para el backend, librería versionada para data. Aclaro: la única rama con protección formal y required reviewers es main — develop y release tienen checks de CI pero no bloqueo por revisor. Después se autentica contra AWS con OIDC: sin secretos largos en GitHub, solo un token efímero por ejecución del workflow. Y finalmente despliega con CDK o SAM al ambiente que la rama indica — develop a DEV, release a STG, main a PROD. Hoy nada de esto está construido. Es lo primero que vamos a levantar en Fase 1, y el desbloqueo crítico es firmar OIDC.

(1 min 30 s) Esta es la arquitectura objetivo. Una sola cuenta AWS, todo en us-east-1, por costo y simplicidad (somos comunidad, no empresa). Aislamiento por IAM y tags, no por cuentas separadas. CDK en TypeScript para infra y frontend; SAM en YAML para backend porque encaja con el monolito Iraca. Data ya empezó a tocar SQS y DLQ en su historia H10 — sí, Data está haciendo infra de verdad. Tres ambientes · tres cuentas

GitFlow define la rama · la rama decide el ambiente.
ADR-CICD-0002 · ADR-CICD-0003 · ADR-INFRA-0002.

develop DEV push automático
release/* STG aprobación manual
main PROD required reviewers
hotfix/* PROD flujo acelerado

Cuenta AWS por ambiente · región us-east-1 · aislamiento por frontera de cuenta.

(1 min 30 s) Esta slide conecta dos cosas que la audiencia ya conoce por separado: git y ambientes. La regla es simple — GitFlow define las ramas, y cada rama decide a qué ambiente despliega. Develop va a DEV automático, ahí experimentamos. Release ramas van a STG con aprobación manual para validar. Main solo entra a PROD con required reviewers. Hotfix tiene su propio carril acelerado a PROD. Tres ambientes, una cuenta AWS por ambiente bajo la OU Skorify (DEV, STG, PROD), región us-east-1, aislamiento por frontera de cuenta. Hoy nada de esto está construido — son los stacks que vamos a levantar en Fase 1 junto con OIDC. La importancia de cerrar los ADR-0002 y 0003 está en que sin esto, cada equipo va a inventar su propia convención de ramas.

SRE · Datadog como plataforma única

Una sola plataforma para logs · métricas · traces · audit. ADR-SRE-0001 (Aceptado).

MVP Fase 1

  • Logs estructurados JSON desde día uno
  • Métricas de aplicación e infraestructura
  • Traces APM en Lambda + frontend
  • CloudTrail audit ingerido

Fase 2 Operación

  • SLOs por servicio
  • RUM (Real User Monitoring)
  • Synthetic monitoring
  • Alertas + on-call rotativo
  • Runbooks accionables

Llamado a los tres equipos: no aceptamos console.log en código que va a producción. Sirve para debug local. No para software robusto. Logs estructurados JSON desde la primera línea.

(1 min 30 s) Datadog es deliberado: si los estudiantes salen del proyecto y entran a industria, ya saben la herramienta más adoptada. Empezamos chiquito —logs, métricas, traces— y crecemos a SLOs y on-call cuando haya tráfico real. Pero hay un mensaje directo para los tres equipos: no quiero ver `console.log` en código que va a producción. Console.log sirve mientras debuggeas en tu máquina, no cuando un servicio falla a las 3 AM y necesitas correlacionar request_id, trace_id y user_id en Datadog. La diferencia entre debug y software robusto es ahí. Logs estructurados JSON desde la primera línea — Pino, Winston o Powertools, lo definimos en el ADR-SRE-0003.

Infraestructura ya tiene código

Módulo S3 en CDK TypeScript · configurable por SSM Parameter Store · sin tocar código. 

export interface S3BucketDefinition {
  /** ID lógico único dentro del módulo (CDK Construct ID). */
  readonly logicalName: string;

  /** Nombre físico del bucket en AWS. */
  readonly bucketName: string;

  /** Habilitar versionado de objetos. */
  readonly versioned: boolean;

  /** Tipo de cifrado del bucket. */
  readonly encryptionType: 'S3_MANAGED' | 'KMS_MANAGED' | 'CUSTOMER_MANAGED';

  /** Alias KMS · requerido cuando encryptionType = 'CUSTOMER_MANAGED'. */
  readonly kmsAlias?: string;

  /** Bucket destino para server access logs (otro bucket de este módulo). */
  readonly serverAccessLogsTargetName?: string;

  /** Días para transición a S3 Intelligent Tiering. */
  readonly lifecycleTransitionDays?: number;

  // Agregar un nuevo bucket = agregar un elemento al array en SSM,
  // sin tocar código del módulo.
}

lib/modules/s3/main.ts · 493 líneas · 275 de tests · módulo networking en camino.

(1 min 15 s) Esto es CDK serio. El módulo no decide qué bucket crear — recibe la lista desde SSM Parameter Store. Agregar un bucket = un cambio en SSM, no un deploy de código. Eso baja la fricción para los equipos de aplicación. Y ya hay 275 líneas de tests unitarios. La sintetización CDK ya genera CloudFormation: `cdk.out/SkorifyInfra-Dev` existe en el repo.

Devcontainer · onboarding en 5 minutos

Un solo "Reopen in Container" → Node 18 + AWS CLI + CDK + SSO listos. 

{
  "name": "Skorify Infraestructura",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:18",
  "features": {
    "ghcr.io/devcontainers/features/aws-cli:1": {}
  },
  "postCreateCommand":
    "npm install -g aws-cdk && npm install",
  "postAttachCommand":
    "bash -lc './.devcontainer/scripts/setup-credentials.sh'"
}

Lo que hace al adjuntarse

  • Instala aws-cdk global + dependencias
  • Configura SSO contra aws-users-groups-manizales
  • Valida sesión con sts get-caller-identity
  • Si falta, ejecuta aws sso login
  • Bootstrap automático de CDKToolkit
  • Extensiones VS Code: AWS Toolkit · Prettier · ESLint

Mateo (@Mateo454) y Michael (@lmichaelrc) guían al equipo en este flujo.

(1 min 15 s) Esto es lo que más impacto tiene en el día a día de los estudiantes. Antes: descargar Node, instalar CDK, configurar AWS CLI, pedir permisos SSO, equivocarse de región, perder dos horas. Ahora: clonar, "Reopen in Container", listo. Si alguien tiene dudas con AWS o CDK, Mateo y Michael son los puntos de contacto. El script `setup-credentials.sh` también bootstrappea CDKToolkit si falta — el primer deploy real del estudiante "simplemente funciona".

Lo que falta · sin maquillaje

Si me detuviera aquí, esta charla sería propaganda. Lo que duele también es parte del avance.

Lo que decidimos pero no cerramos

  • 22 de 28 ADRs siguen en estado Propuesto. Decidir no es firmar, y tenemos firmas pendientes en cosas críticas: OIDC, secrets, naming, branching.
  • Husky vs pre-commit sigue abierto (ADR-CICD-0010). Mientras dudemos, el frontend usa Husky y backend/data no usan nada. La inacción es la decisión por defecto.

Lo que nos toca decidir entre todos

  • Datadog vs CloudWatch (ADR-SRE-0005). Lo revisamos con los líderes en los próximos días: destrabar Datadog, o decidir arrancar con CloudWatch. La meta es tener observabilidad desde el despliegue 0.
  • Sin OIDC, no hay deploy automatizado. Hoy no hemos hecho el primer despliegue ni siquiera en development.

La autocrítica más fuerte: el backend tiene 17 ramas y varias llevan el nombre de quien las creó. El contrato existe, pero ese equipo todavía no lo siente como suyo. Eso no se arregla con un workflow; se arregla con conversación.

(1 min 45 s) Pausa. Hasta aquí pinté un cuadro bonito. Voy a romper el cuadro. Tenemos 22 ADRs sin firmar — eso significa que el 79% de las decisiones técnicas siguen abiertas. Y aquí va el dato más crudo: hoy no hemos hecho el primer despliegue, ni siquiera en development. Sin OIDC no hay pipeline a AWS. Sobre observabilidad: lo vamos a revisar con los líderes en los próximos días, decidimos si destrabamos Datadog o arrancamos con CloudWatch. La meta es la misma: que el primer log estructurado aparezca el mismo día que el primer deploy. El más doloroso: el backend tiene ramas con nombres de personas. Eso me dice que el contrato que firmamos lo siente como suyo el frontend, lo siente como suyo data, pero backend todavía no. Esa conversación me toca a mí, no la resuelve un workflow. Si los estudiantes están escuchando: lo más valioso que pueden hacer esta semana es decirle a un líder de área qué ADR todavía no entienden.
